# Phase Report: v1.0 Phase 5 — AI Provider trait + 4 backends

> 2026-05-17–18 · branch `v1.0-prep` (larkline) · 6 commits

## Outcome

Phase 5 lands the agent layer foundation: a [`Provider`] trait and
four concrete implementations (Anthropic, OpenAI Responses,
OpenRouter, Ollama). Each provider streams responses over an mpsc
sender, supports tool-use, and surfaces normalized errors so the
agent loop built in Phase 8 doesn't have to know which backend it
called.

The trait is object-safe — the `agent::build_provider` factory reads
`[ai] provider = "..."` from config, looks up the API key from the
existing secrets pipeline (Keychain → .env → process env), and
returns a `Box<dyn Provider>`. Switching providers is a config edit;
no recompile.

Phase 6 (single-shot AI plugin) and Phase 8 (tool-use agent) build
on top. No host-side wiring outside `src/agent/` is touched yet —
the providers are reachable from tests but the TUI doesn't surface
them until Phase 6 lands.

## Architecture

```
src/agent/
├── mod.rs             pub fn build_provider(ai_config, secrets) -> Box<dyn Provider>
├── provider.rs        Provider trait + AskRequest + Message + ContentBlock
│                      + ToolDefinition + ProviderEvent + StopReason + Role
├── error.rs           ProviderError { Auth, RateLimited, Api, Network,
│                                      Malformed, Config } + is_retryable
├── anthropic.rs       AnthropicProvider (Messages API, named SSE events,
│                      input_json_delta buffering, prompt caching on last tool)
├── openai.rs          OpenAiResponsesProvider (Responses API, named SSE
│                      events, function_call_arguments.done emits ToolUse)
└── openai_chat.rs     OpenAiChatProvider (Chat Completions, anonymous SSE
                       chunks ending with [DONE], factories for OpenRouter +
                       Ollama with optional API key)
```

### Provider trait shape

```rust
#[async_trait]
pub trait Provider: Send + Sync + Debug {
    fn name(&self) -> &'static str;
    async fn ask(
        &self,
        request: AskRequest,
        events: tokio::sync::mpsc::UnboundedSender<ProviderEvent>,
    ) -> Result<(), ProviderError>;
}
```

Streaming flows over `UnboundedSender<ProviderEvent>` to mirror the
existing `EngineEvent::PartialOutput` pattern. The agent loop will
spawn `ask` on a Tokio task and pump the receiver into the TUI.

### `ProviderEvent` taxonomy

* `TextDelta(String)` — assistant text streaming, concatenate to
  build full response.
* `ToolUse { id, name, args }` — model wants to invoke a tool. The
  `id` is the provider-issued call ID that must accompany the
  matching `ContentBlock::ToolResult` on the next turn.
* `Usage { input_tokens, output_tokens }` — emitted once per stream
  for cost tracking. Providers vary on input_tokens accuracy.
* `Done { stop_reason }` — terminal event. `StopReason` is
  normalized: `EndTurn`, `ToolUse`, `MaxTokens`, `StopSequence`,
  `Other(String)`.

### `AiConfig`

```toml
[ai]
provider             = "anthropic"     # anthropic | openai | openrouter | ollama
model                = ""              # blank = provider default
max_tokens           = 0               # 0 = provider default
openrouter_base_url  = ""              # blank = openrouter.ai/api/v1
ollama_base_url      = ""              # blank = localhost:11434/v1
```

API keys never live in `config.toml`. Three secret names are
declared at startup so `lark secret set <KEY>` works:

* `ANTHROPIC_API_KEY` → Anthropic
* `OPENAI_API_KEY` → OpenAI
* `OPENROUTER_API_KEY` → OpenRouter
* (Ollama has no key — local server, no auth)

## Per-provider notes

### Anthropic (`src/agent/anthropic.rs`)

* Endpoint: `https://api.anthropic.com/v1/messages`
* Headers: `x-api-key`, `anthropic-version: 2023-06-01`
* System prompt at top-level `system`, not in messages.
* Message content is a list of `{type, ...}` blocks. Tool use uses
  `type: "tool_use"` (assistant) and `type: "tool_result"` (user).
* Tools use `input_schema` (not `parameters`). Prompt caching
  enabled on the *last* tool entry — Anthropic's `cache_control`
  applies to the marked block plus everything preceding, so one
  marker covers the entire list. Saves ~40–70% on multi-turn agent
  loops re-sending the same tools.
* SSE events: `content_block_start`, `content_block_delta`,
  `content_block_stop`, `message_delta`, `message_stop`, `error`,
  `ping`. Tool-use arguments stream as `input_json_delta` partial
  strings that we buffer until `content_block_stop`, then parse and
  emit as a single `ProviderEvent::ToolUse`.

### OpenAI Responses (`src/agent/openai.rs`)

* Endpoint: `https://api.openai.com/v1/responses`
* Auth: `Authorization: Bearer <key>`
* System prompt in top-level `instructions` (NOT a system-role
  message — that's the Chat Completions pattern).
* Message array named `input`. Content parts use `input_text` for
  user, `output_text` for assistant.
* Tool definitions are flat `{type: "function", name, description,
  parameters}` — no nesting.
* Tool use produces standalone `function_call` items in the input
  array, separate from message items. Tool results are
  `function_call_output` items. Both carry `call_id`.
* SSE events: `response.output_item.added` (captures call_id),
  `response.output_text.delta` (text), `response.function_call_
  arguments.done` (emits ToolUse — the `done` event carries the
  complete arguments string AND function name, so no buffering),
  `response.completed` (Done + Usage), `response.error`. Other
  event types (~50 total) silently ignored.
* StopReason: `completed` → EndTurn (or ToolUse if any function_call
  appeared); `incomplete` with `reason: max_output_tokens` →
  MaxTokens.

### OpenRouter + Ollama (`src/agent/openai_chat.rs`)

Single `OpenAiChatProvider` parametrized by base URL + optional API
key. Two factory functions:

* `openrouter(api_key, base_url)` — defaults base URL to
  `https://openrouter.ai/api/v1`. Adds HTTP-Referer and X-Title
  headers OpenRouter uses for analytics. Rejects blank API keys.
* `ollama(base_url)` — defaults base URL to
  `http://localhost:11434/v1`. No API key required.

Both speak OpenAI Chat Completions wire format:

* Endpoint: `<base_url>/chat/completions`
* Request uses `messages` (with `role: "system"` entry for system
  prompts).
* Tools wrap function spec under nested `function` key:
  `{type: "function", function: {name, description, parameters}}`.
* Tool calls in assistant messages live in `tool_calls[]` with
  nested `function.arguments` as a JSON string.
* Tool results are standalone `role: "tool"` messages with
  `tool_call_id`.
* SSE has no named events — every chunk is `data: <json>` and the
  stream ends with literal `data: [DONE]`. `finish_reason` on the
  last chunk drives stop_reason.
* `stream_options.include_usage = true` requested so a dedicated
  final chunk carries token counts.

Tool-call accumulation: the first chunk has `index + id +
function.name`; subsequent chunks have partial `function.arguments`.
On `finish_reason: "tool_calls"`, accumulated tools are drained in
index order and emitted as `ProviderEvent::ToolUse` events.

`is_error` on `ContentBlock::ToolResult` has no native equivalent;
failed results get prefixed with `"ERROR: "` in the content body so
the model can recover.

## Wire-format quick reference

| Field | Anthropic | OpenAI Responses | OpenAI Chat (OR/Ollama) |
|---|---|---|---|
| System prompt | top-level `system` | top-level `instructions` | `role:"system"` message |
| Message array | `messages` | `input` | `messages` |
| Text content | `{type:"text", text}` | `{type:"input_text"\|"output_text", text}` | string (or null for tool-only) |
| Tool def schema field | `input_schema` | `parameters` (flat) | `function.parameters` (nested) |
| Tool def discriminator | n/a (no `type`) | `type:"function"` (flat) | `type:"function"` + nested |
| Assistant tool call | `{type:"tool_use", id, name, input}` block | standalone `function_call` item | `tool_calls[].function` |
| Tool result | `{type:"tool_result", tool_use_id, content}` block | standalone `function_call_output` item | `role:"tool"` message |
| Tool call id field | `id` | `call_id` | `id` |
| Args wire format | JSON value | JSON string | JSON string |
| Stream end marker | `message_stop` event | `response.completed` event | `data: [DONE]` literal |
| Prompt caching | `cache_control` per tool | none | none |

  baseline: 9 Anthropic + 12 OpenAI Responses + 13 OpenAI Chat +

Unit tests cover each provider's request body serialization (system
field placement, tool definition shape, tool-use/result block
mapping, system prompt handling) and SSE dispatch (text delta
streaming, tool-call accumulation across chunks, stop reason
mapping, error classification, usage emission). All run against
hand-written event fixtures from the published SSE event schemas —
no real API access required.

Real-API smoke testing lives in the separate smoke runbook
([phases/v1.0-phase-5-ai-provider-smoke-runbook.md](./v1.0-phase-5-ai-provider-smoke-runbook.md))
and requires the user to have one or more provider API keys in
Keychain.

## Open follow-ups

1. **OpenRouter model capability filter** — the v1.0 plan called
   for a `/models` capability check to warn when the selected model
   doesn't support tool-use. Deferred to v1.x; users see a runtime
   error from OpenRouter if they pick an unsupported model, which
   is acceptable for the launch.
2. **Anthropic retry-after parsing** — the Anthropic 429 response
   doesn't currently include retry_after in the body; the value
   lives in the HTTP `retry-after` header which we don't capture.
   Defaults to 60s; tighten if rate limits become a real issue in
   beta testing.
3. **Real-API integration tests in CI** — would require storing API
   keys as CI secrets and budgeting for the test cost. Deferred;
   unit tests against published event schemas cover the parsing
   logic, and the smoke runbook covers end-to-end live API.
4. **Token cost estimation** — usage events arrive per response;
   summing across an agent loop turn-by-turn is a UI concern for
   Phase 8. Provider layer already surfaces the numbers.

## Phase 6 ready

Phase 5 leaves the codebase ready for Phase 6 (AI single-shot
plugin). Phase 6 will:

1. Add an `examples/plugins/ai/` directory with `ask.lua`.
2. Wire a host fn (`lark.ai_ask(prompt, model)`) that constructs an
   `AskRequest`, hands it to the configured `build_provider`, and
   streams text deltas back to the plugin output.
3. Reuse the existing `EngineEvent::PartialOutput` for streaming
   render in the TUI.

No provider trait changes anticipated for Phase 6 — the streaming
+ event taxonomy already covers single-shot needs. Tool-use plumbing
(`ContentBlock::ToolUse` / `ToolResult`, agent loop) waits for
Phase 7 (tool registry) + Phase 8 (agent UI).
