# Phase Report: v1.0 Phase 2 — macOS Helper (EventKit)

> 2026-05-12 · branch `v1.0-prep` (larkline) · 5 commits

## Outcome

Phase 2 complete in one focused session — substantially under the 2-week
budget. The Swift helper `larkline-macos-helper` ships with `lark` on
macOS and exposes EventKit (Calendar) over a line-delimited JSON
protocol on stdin/stdout. The lark Calendar plugin in Phase 3 will
shell out to it for rich event data.

Two sub-phases were dropped or rescoped during execution after
research surfaced platform limitations:

- **Phase 2.E (`respond_to_invite`)** — DROPPED. EventKit's
  `EKParticipant.participantStatus` is read-only on iOS and macOS
  (Apple docs + WWDC23). Cal v2's "RSVP" action in Phase 3 will
  instead shell out to `/usr/bin/open ical://event/<id>` from Lua;
  user clicks accept/decline in Calendar.app.
- **EKVirtualConferenceDescriptor** — DROPPED from `events_for_range`
  meeting-URL extraction. Its public Swift API for synchronous reads
  is unstable across SDK versions. The three-tier fallback
  (event.url → regex(location) → regex(notes)) covers both the modern
  case (Calendar.app populates event.url from conferenceData) and the
  legacy case (Outlook-imported events with the URL in notes).

## Helper protocol summary

**Wire format:** one JSON object per line on stdin/stdout.

| Direction | Shape |
|---|---|
| Server → Client (startup) | `{"kind":"hello","helper_version":"0.1.0","protocol_version":1}` |
| Client → Server (request) | `{"id":"<corr>","command":"<name>","args":{...}}` |
| Server → Client (ok) | `{"id":"<echo>","ok":true,"data":{...}}` |
| Server → Client (error) | `{"id":"<echo>","ok":false,"error":"..."}` |

**Commands in v1.0:**

- `version` — returns `{helper_version, protocol_version}`
- `ping` — returns `{pong: true}` (smoke test)
- `list_calendars` — returns all event calendars with id, title, source,
  allowsModifications, hex color
- `events_for_range` — takes `{start_iso, end_iso, calendar_ids?}`,
  returns events with full fields including extracted meetingURL and
  attendee list (status, role, isCurrentUser flag)

`Empty lines silently skipped; malformed JSON yields an error response
with the id field omitted.

## Decisions made during execution

### Why no MCP server (research finding from planning phase carried forward)

The v1.0 agent palette uses an in-process tool registry, not an MCP
server. The plan originally considered exposing Larkline as an MCP
server for Codex CLI integration; Taylor's call: "we are talking
about doing stuff in lark, not going to codex and controlling lark."
This decision keeps Phase 2 focused on the calendar plugin's data
needs, not multi-client tool exposure.

### Why no EKVirtualConferenceDescriptor

Discovered during Phase 2.D: the Swift API for synchronous reads of
`EKVirtualConferenceDescriptor.urlDescriptors` is unstable. Apple's
docs suggest the `EKEvent.virtualConferenceURLs` accessor only on
iOS; macOS routes through `EKEventStore.fetchConferenceForEvent`
which is async-only. We tried a `Task { } + DispatchSemaphore` bridge
via KVC (`event.value(forKey: "conferenceURL")`) — works on some SDK
versions, doesn't on others, no public guarantees. Dropped in favor
of the simpler regex-over-event.url+location+notes path which covers
both modern (Calendar.app extracts conferenceData → event.url) and
legacy (Outlook → notes) cases.

### Why no programmatic RSVP

EventKit's API surface for events explicitly does not allow modifying
participant status. EKParticipant exposes status as a `get` property
with no `set`. Verified via:
- [Apple Developer Documentation — EKEvent](https://developer.apple.com/documentation/eventkit/ekevent)
- [WWDC23 — Discover Calendar and EventKit](https://developer.apple.com/videos/play/wwdc2023/10052/)

Practical alternatives evaluated:
- AppleScript driving Calendar.app — Calendar.app's scripting dictionary
  has no "respond to invitation" verb either.
- Send iCalendar REPLY via email — possible but requires Mail integration
  (Phase 4 scope); deferred.
- Open Calendar.app to the event — user RSVPs via the native UI.

Chose the third option. Cal v2's RSVP action becomes a shell-out to
`/usr/bin/open ical://event/<id>` from the Lua plugin. The plan +
roadmap were updated to reflect this.

### Universal binary via lipo

CI workflow builds the helper for both arm64 and x86_64 then lipos
them into a single universal binary. Verified locally on Apple
Silicon: `swift build --arch arm64` (cached, 0.07s) + `swift build
--arch x86_64` (2.60s cross-compile) + `lipo -create` produces a
fat Mach-O with both archs; `codesign --sign -` ad-hoc signs it for
distribution.

### Three-tier meeting URL extraction

Regex patterns cover Teams (teams.microsoft.com, teams.live.com),
Zoom (zoom.us/j/, zoom.us/my/), Google Meet (meet.google.com/xxx-xxxx-xxx),
Webex (webex.com/meet/, webex.com/join/). Priority:
1. `EKEvent.url` if it matches a meeting pattern (Calendar.app's
   conferenceData extraction populates this for modern sources)
2. Regex over `event.location` (Outlook's import path)
3. Regex over `event.notes` (legacy CalDAV / .ics imports)

If a v1.0 beta tester reports a missed URL we can extend patterns
or revisit EKVirtualConferenceDescriptor with a better sync wrapper.

## Test results / verification

`swift build -c release` — clean compile, 70KB binary.

Local protocol smoke (batch of 6 requests):
- `version` → ok, returns helper_version 0.1.0 ✓
- `ping` → ok, returns `{pong: true}` ✓
- unknown command → error preserved with request id ✓
- malformed JSON → error with omitted id ✓
- empty line → silently skipped ✓
- request with extra args → handler ignores, ok ✓

EventKit smoke against a real Mac:
- `list_calendars` → 15 calendars across iCloud / Google CalDAV /
  Subscribed / Other sources with hex colors ✓
- `events_for_range` (14-day window) → 9 events with attendees,
  source labels, ISO 8601 dates ✓
- 0/9 had meetingURL extracted (expected — the 9 events were all
  personal/family entries without conference URLs)

Cross-arch + signing:
- `swift build --arch arm64` ✓ 
- `swift build --arch x86_64` ✓ (cross-compile on Apple Silicon)
- `lipo -create` → universal Mach-O with both archs ✓
- `codesign --sign -` → ad-hoc signature attached ✓

SourceKit cross-file diagnostics in the editor (Cannot find type
'Request' etc.) are noise from `main.swift`'s top-level statements.
swiftc itself compiles cleanly. Not a code issue.

## Pre-tag gate (Phase 2)

Phase 2 has no public release tag of its own — it's an intermediate
phase on `v1.0-prep`. Smoke verification is:

1. **Local build**: `cd macos-helper && swift build -c release` returns 0
2. **Local round-trip**: `echo '{"id":"1","command":"version"}' | .build/release/larkline-macos-helper`
   prints the hello line + a valid version response
3. **TCC dialog**: first `list_calendars` invocation triggers the
   macOS Calendar permission prompt (or returns the access-denied
   error if previously denied)
4. **CI builds**: when v1.0 is tagged, the `build-helper` job
   produces a universal binary; the build matrix bundles it into
   macOS tarballs alongside `lark`

See `phases/v1.0-phase-2-macos-helper-smoke-runbook.md` for the full
runbook.
