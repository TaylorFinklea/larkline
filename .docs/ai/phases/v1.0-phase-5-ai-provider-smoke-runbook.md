# v1.0 Phase 5 — AI Provider Smoke Runbook

> 2026-05-18 · branch `v1.0-prep`

Phase 5 lands four [`Provider`] implementations (Anthropic, OpenAI
Responses, OpenRouter, Ollama). Unit tests cover the request/response
shapes against published event schemas; this runbook covers the parts
unit tests can't: real-API authentication, real streaming, and real
tool-use round-trips.

Phase 5 itself doesn't surface AI in the TUI yet — that's Phase 6.
For Phase 5 smoke, you'll invoke the providers programmatically via
a small Rust helper or `cargo test -- --ignored` with real keys.

## Prerequisites

* `cargo build --bin lark` succeeds on `v1.0-prep`.
* For each provider you want to test, set the corresponding secret:
  * `lark secret set ANTHROPIC_API_KEY`
  * `lark secret set OPENAI_API_KEY`
  * `lark secret set OPENROUTER_API_KEY`
  * Ollama: run `ollama serve` locally and `ollama pull llama3.2`
    (or another tool-capable model).

## Section A — Authentication smoke (no model calls)

For each provider, verify that the factory + secrets pipeline finds
the key. This is the quickest signal that config + secrets are wired
right without burning tokens.

```sh
cargo run --bin lark -- secret list
```

Confirm `ANTHROPIC_API_KEY` (and any others you've set) appear. Then
in a Rust scratch file (or `cargo test`):

```rust
let (config, _warnings) = larkline::config::load()?;
let mut secrets = larkline::config::load_secrets();
larkline::config::resolve_keychain_secrets(
    &mut secrets,
    &larkline::config::AI_SECRET_KEYS,
);
let provider = larkline::agent::build_provider(&config.ai, &secrets)?;
assert_eq!(provider.name(), config.ai.provider.as_str());
```

Note: `larkline::agent` and `larkline::config` aren't currently
exposed via `lib.rs`. If you want this exact incantation to work,
add them; otherwise mirror the same call in a test inside
`src/main.rs` or `src/agent/mod.rs`. The unit tests in
`agent::tests` already exercise this path with stub secrets.

Expected: success for whatever provider you've configured; an
`Auth(...)` error mentioning the missing key name otherwise.

## Section B — Anthropic streaming (real call)

Switch to Anthropic in `~/.config/larkline/config.toml`:

```toml
[ai]
provider = "anthropic"
model    = "claude-opus-4-7"   # or claude-3-5-sonnet-latest, etc.
```

In a test or scratch binary:

```rust
use larkline::agent::{build_provider, AskRequest, Message, ProviderEvent};
use tokio::sync::mpsc;

let (tx, mut rx) = mpsc::unbounded_channel();
let provider = build_provider(&config.ai, &secrets)?;
let req = AskRequest {
    system: Some("Be terse. One sentence answers only.".into()),
    messages: vec![Message::user("What's 2+2?")],
    tools: vec![],
    model: config.ai.resolved_model().into(),
    max_tokens: Some(128),
};
let handle = tokio::spawn(async move {
    provider.ask(req, tx).await
});
while let Some(event) = rx.recv().await {
    println!("{event:?}");
}
handle.await??;
```

Expected:

* Several `TextDelta("...")` events containing the answer in
  fragments.
* One `Done { stop_reason: EndTurn }` event.
* One `Usage { input_tokens, output_tokens }` event.
* No `Malformed` errors.

Failure modes to watch for:

* `Auth(...)` → API key wrong or revoked.
* `Network(...)` → DNS / TLS / connection problems.
* `Malformed("SSE data: ...")` → wire format drifted; capture the
  exact data line and update the parser.
* No events at all → check the model name; Anthropic returns 400 on
  unknown model with a useful message body.

## Section C — Anthropic tool-use round-trip

Same setup as Section B, but pass a tool definition and a prompt
that will trigger it:

```rust
use serde_json::json;
use larkline::agent::ToolDefinition;

let req = AskRequest {
    system: Some("Use tools when the user asks about weather.".into()),
    messages: vec![Message::user("What's the weather in San Francisco?")],
    tools: vec![ToolDefinition {
        name: "get_weather".into(),
        description: "Get current weather for a city.".into(),
        input_schema: json!({
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        }),
    }],
    model: config.ai.resolved_model().into(),
    max_tokens: Some(512),
};
```

Expected sequence:

1. Possibly some `TextDelta(...)` events with planning text.
2. A `ToolUse { id, name: "get_weather", args }` event where
   `args = {"city": "San Francisco"}` (or "SF" or similar).
3. A `Done { stop_reason: ToolUse }` event.
4. A `Usage` event.

To complete the loop manually, build a follow-up `AskRequest` with
the tool result:

```rust
let req2 = AskRequest {
    system: req.system.clone(),
    messages: vec![
        Message::user("What's the weather in San Francisco?"),
        Message {
            role: Role::Assistant,
            content: vec![ContentBlock::ToolUse {
                id: "<id from event>".into(),
                name: "get_weather".into(),
                input: json!({"city": "San Francisco"}),
            }],
        },
        Message {
            role: Role::User,
            content: vec![ContentBlock::ToolResult {
                tool_use_id: "<id from event>".into(),
                content: "72F and sunny".into(),
                is_error: false,
            }],
        },
    ],
    ..req
};
```

Expected: `TextDelta` events with a natural-language weather
response that incorporates "72F and sunny", followed by
`Done { stop_reason: EndTurn }`.

## Section D — OpenAI Responses streaming

Switch to OpenAI:

```toml
[ai]
provider = "openai"
model    = "gpt-4o"
```

Run the Section B test. Expected: same `TextDelta` + `Done` + `Usage`
shape. OpenAI Responses uses different SSE event names internally
but the dispatcher normalizes to identical `ProviderEvent`s.

Wire-format gotchas to watch for:

* If the response comes back as a `Malformed` error mentioning
  `response.output_text.delta`, the Responses API may have evolved
  beyond what we parse. Capture the SSE stream and check
  `src/agent/openai.rs` for the event names we look for.
* The `incomplete_details.reason` mapping is best-effort; an unknown
  reason surfaces as `StopReason::Other(reason_string)` which the
  agent loop should treat as an error.

For tool-use: rerun the Section C scenario with the OpenAI provider.
The internal arguments format is a JSON string (not a value), but
the dispatcher parses it before emitting `ProviderEvent::ToolUse`,
so the result is provider-uniform.

## Section E — OpenRouter

Switch:

```toml
[ai]
provider          = "openrouter"
model             = "anthropic/claude-3.5-sonnet"   # or any tool-capable model
```

Run Section B. Expected: identical event shape to the others.
OpenRouter is OpenAI Chat Completions transport, so:

* SSE chunks are anonymous `data: <json>` lines ending with
  `data: [DONE]`.
* Tool calls stream incrementally and emit on
  `finish_reason: "tool_calls"`.

Failure modes specific to OpenRouter:

* `Api("HTTP 400: ...model does not support tool use...")` — pick a
  different model. Tool-capable models include
  `anthropic/claude-3.5-sonnet`, `openai/gpt-4o`,
  `meta-llama/llama-3.3-70b-instruct`. OpenRouter's `/models`
  endpoint lists capabilities; the v1.0 plan's capability filter
  was deferred to v1.1.

For tool-use: rerun Section C. Note that OpenRouter's `tool_calls`
in the message format may need slight adaptation — if you see
`Malformed` errors mentioning tool_call structure, capture the SSE
stream and check `src/agent/openai_chat.rs` SseDispatcher.

## Section F — Ollama (local)

Install Ollama if you haven't:

```sh
brew install ollama
ollama serve &
ollama pull llama3.2   # 2GB; tool-use capable
```

Switch:

```toml
[ai]
provider = "ollama"
model    = "llama3.2"
```

Run Section B against `http://localhost:11434/v1/chat/completions`.
No API key needed; the local server doesn't auth.

Expected: same `ProviderEvent` shape. Local model quality is lower
than commercial APIs — expect terser, less polished output.

Tool-use on Ollama requires a tool-capable model. Llama 3.2,
Mistral 7B Instruct v0.3+, and Qwen 2.5 7B+ all support it. Smaller
or older models will ignore the tools array and respond in prose.

Failure modes specific to Ollama:

* `Network("connection refused")` → `ollama serve` not running.
* Empty/garbled responses → model isn't tool-capable; try
  `ollama pull llama3.2` (or a different model).

## Section G — Configuration switching

End-to-end: change `[ai] provider` between runs without touching
code. Verify each provider works:

```sh
# Edit ~/.config/larkline/config.toml; set provider = "anthropic"
cargo run --bin lark -- ...
# Then set provider = "openai"
# Then set provider = "openrouter"
# Then set provider = "ollama"
```

If any provider that worked yesterday stops working today, the wire
format has likely drifted. Capture the raw SSE stream and file a
follow-up. The unit tests pin expected event shapes; updating them
to match new formats is the canonical fix.

## Pass criteria

For Phase 5 to be considered shipped:

* [ ] At least one provider passes Sections A + B (auth + simple
      streaming) end-to-end on your machine.
* [ ] At least one provider passes Section C (tool-use round-trip).
* [ ] `cargo test --bin lark` → 188 passed; `--lib` → 58 passed;
      `cargo clippy --bin lark -- -D warnings` → clean.

The unprivileged provider (Ollama) is the cheapest way to validate
without burning tokens — if you have Ollama set up, treat it as
required-pass. Anthropic + OpenAI + OpenRouter can be smoke-tested
when their respective keys are set.
