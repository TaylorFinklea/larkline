# Phase 8 — Agent Loop Architecture Spec

> Drafted 2026-05-23 (post-Phase 5 / pre-Phase 6). Locks in the
> structural decisions for the agent runtime before any of its code is
> written. **Phase 7 (tool registry from manifests) shapes a subset of
> these.**

## Prior art

This spec borrows heavily from
[earendil-works/pi](https://github.com/earendil-works/pi) — specifically
`packages/agent/src/agent-loop.ts` + the design docs at
`packages/agent/docs/{agent-harness,hooks,observability,durable-harness}.md`.
Pi is a TypeScript implementation of the same problem we're solving;
the patterns translate cleanly to Rust + Larkline's existing surfaces.
Notes on what we adopt vs. skip live in the per-section "Why this
shape" callouts.

## Goals

A v1.0 agent loop that can:

1. Run a multi-turn conversation that calls Larkline plugins as tools.
2. **Gate destructive tool calls behind user approval** (the "dry-run
   plan preview" called out in `v1.0-plan.md`).
3. **Accept mid-turn user input** ("steer the agent") without canceling
   the turn.
4. **Resume after a crash** — sessions persist to disk, can be reopened.
5. Produce an **audit log** of what tools ran with what arguments.
6. Stay under ~1500 LOC of new Rust in `src/agent/`.

Non-goals for Phase 8 (deferred to v1.x):

- Context compaction (long sessions just fail with a token-limit error
  in v1.0; we surface it cleanly).
- Tree navigation / forks / clones (linear sessions only).
- Plugin-registered hooks (only built-in hooks ship; the trait is
  exposed so v1.1 can add plugin hooks).
- "Skills" as a separate construct (Larkline's plugin manifests already
  fill that role).

### State machine (`AgentPhase`)

```rust
pub enum AgentPhase {
    Idle,             // accepting new prompts
    Turn,             // model is generating + tools may be dispatching
    AwaitingApproval, // tool plan submitted to user; loop is paused
    Retry,            // transient provider error; backing off before retry
}
```

Structural operations (`prompt`, `abort_session`, `switch_model`)
require `Idle` and synchronously transition before any `await`.
Operations from outside the loop that *are* valid during `Turn` (queue
operations, approval responses) bypass the phase gate by going through
their own queue endpoints — never by mutating phase directly.

| Operation | Required phase | Effect |
|---|---|---|
| `prompt(msg)` | `Idle` | `Idle` → `Turn` → ... → `Idle` |
| `steer(msg)` | `Turn` | enqueue; injected into next provider call within turn |
| `follow_up(msg)` | any | enqueue; consumed when current turn ends |
| `approve_plan(decision)` | `AwaitingApproval` | `AwaitingApproval` → `Turn` |
| `abort()` | `Turn` \| `AwaitingApproval` | clear steering, cancel provider stream, → `Idle` |

**Why this shape:** without explicit phase state, "reject ops while
busy" becomes scattered `if self.is_running { ... }` checks throughout
the code. Pi's `AgentHarnessError { code: "busy" }` pattern combined
with a `require_phase()` helper makes the invariants legible at every
public entry point.

### Turn snapshot

A `TurnSnapshot` is the immutable view of harness state captured at
turn start:

```rust
pub struct TurnSnapshot {
    request: AskRequest,                   // including resolved tools
    model: String,
    thinking_level: ThinkingLevel,         // future Anthropic extended thinking
    system_prompt: String,
    tools: Vec<ToolDefinition>,
    active_tool_filter: Option<HashSet<String>>,  // subset enabled this turn
    cancel_token: CancellationToken,
}
```

The harness has a live "config" struct (mutable from settings UI),
plus the snapshot which is created at `Idle → Turn` via
`materialize_snapshot(&self.config) -> TurnSnapshot`. Settings UI
writes affect the *next* turn only.

**Why this shape:** Larkline's `FormField` settings UI is live. Without
snapshotting, a settings toggle in the middle of a tool call races the
provider request. Pi snapshots the request once and reads from it for
the rest of the turn; we match that.

### Two-queue model

```rust
struct MessageQueues {
    steering:  VecDeque<Message>,   // mid-turn user input
    follow_up: VecDeque<Message>,   // queued continuation after turn
}
```

| Queue | When consumed | What `abort()` does to it |
|---|---|---|
| **Steering** | Drained into the next assistant call within the same turn; the harness polls between provider chunks | Cleared |
| **Follow-up** | Drained at turn boundary; non-empty queue continues the loop with the queued messages becoming the next user turn | **Preserved** — survives abort, replays into the next prompt |

**Why this shape:** This is the single most important UX pattern from
pi. It's what makes the agent feel responsive instead of locked. The
naive "block until done, then accept next input" pattern is the
default footgun for hand-rolled agents; baking the queues in from the
start avoids retrofitting.

### Hook trait

```rust
#[async_trait]
pub trait AgentHook: Send + Sync {
    /// Approve or block a tool call before dispatch.
    async fn before_tool_call(
        &self,
        ctx: &BeforeToolCallCtx,
    ) -> Option<BlockDecision> { None }

    /// Patch a tool result before it's added to the conversation.
    async fn after_tool_call(
        &self,
        ctx: &AfterToolCallCtx,
    ) -> Option<PatchedResult> { None }

    /// Decide whether to stop the loop after the current turn.
    async fn should_stop_after_turn(
        &self,
        ctx: &TurnEndCtx,
    ) -> bool { false }

    /// Mutate the request before the next turn starts (model swap,
    /// context transform).
    async fn prepare_next_turn(
        &self,
        ctx: &PrepareNextTurnCtx,
    ) -> Option<TurnUpdate> { None }
}

pub enum BlockDecision {
    Allow,                                 // explicit allow (rare)
    Block { reason: String },              // block this tool call
    WaitForApproval { plan: ToolCallPlan }, // pause loop, ask user
}
```

Hooks are registered in `AgentHarness::new`. v1.0 ships one built-in
hook:

- **`DryRunApprovalHook`** — for any tool call where the matching
  command has `destructive = true` in its manifest, returns
  `BlockDecision::WaitForApproval`. Loop transitions to
  `AwaitingApproval`, surfaces the plan via an `EngineEvent::AgentEvent
  { kind: PlanForApproval(_) }`, and waits for `approve_plan()` to
  resume.

v1.0 keeps the hook trait `pub`-but-not-discoverable: no plugin
registration mechanism yet. v1.1 will add `lark.register_agent_hook()`
in Lua + a manifest section. The trait shape is locked in v1.0 so v1.1
doesn't need a breaking change.

**Why this shape:** the dry-run plan preview from `v1.0-plan.md` *is*
`before_tool_call → WaitForApproval`. Building it as a built-in hook
(not a hardcoded if-statement in the loop) means the same machinery
that gates destructive tools can later gate anything else (rate
limits, cost ceilings, content filters). Pi's `beforeToolCall { block,
reason }` pattern is the same shape; we add `WaitForApproval` because
async user input is core to our story.

### Session persistence (JSONL append-only)

Sessions live at `$XDG_STATE_HOME/larkline/sessions/<session-id>.jsonl`.
One JSON object per line. Each entry has `id` (UUID v7 for time
ordering) and `parent_id` (the previous entry; `null` for the session
header).

```jsonl
{"type":"session","version":1,"id":"...","created_at":"2026-05-23T..."}
{"type":"user","id":"...","parent_id":"...","message":{...}}
{"type":"assistant","id":"...","parent_id":"...","message":{...}}
{"type":"tool_call","id":"...","parent_id":"...","call_id":"...","name":"calendar__list_events","args":{...}}
{"type":"tool_result","id":"...","parent_id":"...","call_id":"...","content":"...","is_error":false}
{"type":"plan_approved","id":"...","parent_id":"...","plan_id":"...","decision":"approved"}
{"type":"turn_end","id":"...","parent_id":"...","stop_reason":"end_turn","usage":{...}}
{"type":"leaf","id":"...","entry_id":"..."}
```

Pi's full taxonomy includes branch-summary entries, compaction
entries, and label entries; we ship only the linear subset above.
Adding the others is forward-compatible (new `type` values are
ignored by older readers, per JSON Lines convention).

**Why this shape:**

1. **Crash recovery is free.** Replay the file, reduce to current
   state. The `leaf` entry tracks the last committed position.
2. **Audit trail is built-in.** No separate "audit log" file needed
   for the conversation itself — the session log *is* the audit trail.
3. **Resumable sessions are free.** `lark ai-resume <id>` opens the
   file and continues.
4. **Linear → tree is additive.** v1.1 adds `parent_id` traversal +
   `/fork` + `/tree`; v1.0 stores the same `parent_id` field, just
   only ever appends to one leaf.

Writer model: a per-session `tokio::sync::Mutex<BufWriter<File>>` that
flushes after every entry. The write barrier matches the loop's "save
point" — same idea as pi's pending-writes queue, simpler
implementation because we don't need to defer writes.

### Audit log (structured, safe-metadata-only)

Separate from the session log: a single rolling
`$XDG_STATE_HOME/larkline/agent-audit.log` that captures **only safe
metadata** for ops-review use cases.

```jsonl
{"ts":"...","trace_id":"...","span_id":"...","name":"agent.turn","kind":"start"}
{"ts":"...","trace_id":"...","span_id":"...","name":"agent.tool_call","kind":"start","tool":"calendar__list_events","destructive":false}
{"ts":"...","trace_id":"...","span_id":"...","name":"agent.tool_call","kind":"end","tool":"calendar__list_events","duration_ms":143,"status":"ok"}
{"ts":"...","trace_id":"...","span_id":"...","name":"ai.provider.request","kind":"end","provider":"anthropic","model":"claude-opus-4-7","input_tokens":2341,"output_tokens":189,"duration_ms":3420}
{"ts":"...","trace_id":"...","span_id":"...","name":"agent.turn","kind":"end","stop_reason":"end_turn"}
```

**Excluded by default:** prompt text, assistant text, tool args, tool
results, API keys, headers. Pi's `"Content capture can be opt-in
later"` pattern — we may add a `[audit] capture_content = true` in
v1.1 for power users.

**Why this shape:** the Phase 8 plan in `v1.0-plan.md` calls for an
audit log; pi shows that separating "what happened" (safe metadata)
from "what was said" (content) is the right axis. Content already
lives in the session log; the audit log is the cross-session ops view.

## Public Rust surface

```rust
// src/agent/loop.rs
pub struct AgentHarness {
    config: AgentConfig,
    phase: AgentPhase,
    provider: Box<dyn Provider>,
    session: SessionLog,
    audit: AuditLog,
    queues: MessageQueues,
    hooks: Vec<Box<dyn AgentHook>>,
    cancel_token: CancellationToken,
}

impl AgentHarness {
    pub fn open(config: AgentConfig, session_id: Option<Uuid>) -> Result<Self, AgentError>;

    pub async fn prompt(&mut self, msg: Message) -> Result<TurnOutcome, AgentError>;
    pub fn steer(&mut self, msg: Message) -> Result<(), AgentError>;
    pub fn follow_up(&mut self, msg: Message) -> Result<(), AgentError>;
    pub async fn approve_plan(&mut self, decision: PlanDecision) -> Result<(), AgentError>;
    pub fn abort(&mut self);

    pub fn phase(&self) -> AgentPhase;
    pub fn session_id(&self) -> Uuid;
}

pub enum TurnOutcome {
    Completed,
    AwaitingApproval(ToolCallPlan),
    Aborted,
}

pub enum AgentError {
    Busy { current_phase: AgentPhase, attempted: &'static str },
    Provider(ProviderError),
    Session(std::io::Error),
    Hook(String),
}
```

Engine integration: a new `EngineEvent::AgentEvent { kind: AgentEventKind }` variant carries
streaming output to the TUI:

```rust
pub enum AgentEventKind {
    TextDelta(String),
    ToolCallStart { call_id: String, name: String },
    ToolCallEnd { call_id: String, is_error: bool },
    PlanForApproval(ToolCallPlan),
    TurnEnd { stop_reason: StopReason },
}
```

This routes through the same `mpsc::Sender<EngineEvent>` the rest of
the engine uses — no new transport.

## Tradeoffs with the v1.0-plan.md commitments

| `v1.0-plan.md` says | Spec aligns | Notes |
|---|---|---|
| `src/agent/{provider,anthropic,openai,loop,planner,audit}` | ✅ + `snapshot,hooks,approval,session` | Lock in modules above. `planner` becomes `approval`. |
| "Three-layer safety (manifest, destructive, dry-run plan)" | ✅ | Layers 1+2 are Phase 7 (manifest); layer 3 is `DryRunApprovalHook` |
| "Audit log at `$XDG_STATE_HOME/larkline/agent-audit.log`" | ✅ | Schema above |
| "No engine-level changes" | ⚠ partial | One new `EngineEvent::AgentEvent` variant. Additive. Justified for streaming routing. |
| "Reused infrastructure: `crate::actions::execute()`" | ✅ | Tool dispatch calls into existing dispatcher; tool result = its `PluginOutput` rendered as text |

## Decisions locked in (resolved 2026-05-24 via harness-deck `20260523-pi-mono-study`)

1. **Cancellation token plumbing → Phase 7.** Phase 7 lands the
   breaking-but-additive trait change: `Plugin::execute(&self, cancel:
   &CancellationToken)` (and matching `crate::actions::execute`). Every
   existing impl gets the param added, even if they ignore it. Justified
   because the agent must be able to abort slow tools.

2. **`thinking_level` scaffolded in `TurnSnapshot` from day one.**
   Field exists in the struct; Anthropic provider reads it,
   OpenAI/OpenRouter/Ollama providers ignore it (no-op). Avoids a
   restructure when Anthropic extended thinking lands in the v1.0
   timeframe.

3. **Approval UX: all-or-nothing.** `DryRunApprovalHook` returns one
   `BlockDecision::WaitForApproval { plan }` for the whole plan; user
   gives one Enter to approve or one `n` to reject. Per-tool toggles
   deferred to v1.1 if real demand surfaces. Matches pi-mono behavior.

4. **Session IDs are UUID v7.** Add `features = ["v7"]` to the `uuid`
   dep. Time-ordered v7 IDs make `ls sessions/` show newest-first for
   free and remove the need for a separate `created_at` sort step in
   `lark ai-resume`.

## Implementation sequence

Phase 8 lands in sub-phases to keep PRs reviewable:

- **8.A** — `AgentPhase` + `AgentHarness::open/prompt/abort` skeleton;
  no tools, no hooks. Drives the provider, streams output, persists
  session. ~400 LOC.
- **8.B** — Hook trait + `DryRunApprovalHook` + `AwaitingApproval`
  phase + `approve_plan()`. Tools wired in from Phase 7's registry.
  ~300 LOC.
- **8.C** — Steering + follow-up queues; mid-turn poll in the inner
  loop. ~150 LOC.
- **8.D** — Audit log with structured events. ~150 LOC.
- **8.E** — TUI plugin `examples/plugins/ai/agent.lua` that drives
  the harness via a new `lark.agent_*` host fn surface. Plugin-only.
- **8.F** — Phase report + smoke runbook + handoff doc updates.

Total Rust budget: ~1000 LOC + tests, on track for the ~1500 LOC ceiling.
