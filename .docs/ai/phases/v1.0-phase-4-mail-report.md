# Phase Report: v1.0 Phase 4 — Mail plugin (osascript)

> 2026-05-12 · branch `v1.0-prep` (larkline) · 2 commits

## Outcome

Phase 4 shipped 4 of 5 planned sub-phases in two focused sessions. The
Mail plugin now provides Inbox, Mail Search, Triage, and New Mail
commands via osascript/JXA against Apple Mail. Phase 4.E (mailbox
switcher with chain action) deferred to v1.x — the chain-action
plumbing complexity outweighed v1.0 value when INBOX is the high-traffic
path and users can already navigate Mail.app's sidebar directly.

Performance acceptable: warm-cache list of 12-30 messages with bodies
inlined takes ~3s. Search across all inboxes ~0.3s. Mutating actions
(mark read, flag, archive) ~0.5-1s each. JXA bridge proves out as the
right pattern — same approach used by mail-app-cli, apple-mail-mcp,
fruitmail-cli in the wild.

## Plugin structure

```
examples/plugins/mail/
├── manifest.toml      # 4 commands: Inbox (mi), Mail Search (ms), Triage (mt), New Mail (mc)
├── lib.lua            # Canonical: jxa_run, time_ago, format_message_row, urlencode, error_item
├── inbox.lua          # Read-only inbox; 1 action per row (Open in Mail.app)
├── search.lua         # Form (query) -> JXA whose-filter; up to 100 matches
├── triage.lua         # Inbox + 6 mutating actions per row (mark/flag/archive/delete/reply/forward)
└── compose.lua        # Form (To, Subject) -> JXA opens Mail.app composer; user types body + sends
```

Each command's Lua file is self-contained: helpers from lib.lua are
inlined with `-- SHARED:` markers since the mlua sandbox has no
require(). lib.lua is the canonical source for diffing when one file
drifts.

## Wire-format additions

None. Phase 4 is pure plugin work. The `lark.exec_io` host fn added in
Phase 3.A handles all stdin-piping needs (osascript -l JavaScript reads
JXA from stdin).

## JXA patterns used

### Read query (Inbox, Search, Triage)

Single batched call returns N messages with bodies inline. Loop over
enabled accounts, take the last 30 from each INBOX, sort all results
newest-first across accounts. Body capped at 5KB per message.

### Mutation dispatch (Triage)

`shell` action kind with inline JXA:
```
osascript -l JavaScript -e '
  const m = Application("Mail")
    .accounts.byName("Google")
    .mailboxes.byName("INBOX")
    .messages.whose({messageId: "abc@host"})()[0];
  if (m) { m.readStatus = true }
'
```

`whose({messageId: ...})` scoped to a specific (account, mailbox) is
fast (~0.5s). The `js_str` helper uses `lark.json.encode` to safely
produce JS string literals from Lua strings — no shell injection
because args go to osascript directly (no shell parsing).

### Compose (New Mail)

```
const Mail = Application("Mail");
const msg = Mail.OutgoingMessage({subject: "...", content: "", visible: true});
Mail.outgoingMessages.push(msg);
msg.toRecipients.push(Mail.ToRecipient({address: "..."}));
```

Mail.app composer window appears in foreground. User types body and
clicks Send. No programmatic SMTP — preserves account picker, signature,
threading. The action carries `confirm = true` to gate the side-effect.

## Decisions made during execution

### URL scheme: `message:<urlencoded-Message-ID>`

Apple Mail's `message:` URL scheme opens a specific message by Message-ID.
The Message-ID needs to be wrapped in `<...>` and percent-encoded.
Used as the primary "Open in Mail.app" action for every row.

### Body search excluded from v1.0

`whose({content: {_contains: q}})` would search message bodies, but the
Apple Event bridge crosses the full body of every candidate message —
order-of-magnitude slower than subject+sender search. For v1.0, Mail
Search is metadata-only (subject + sender). Users can fall back to
Mail.app's native Cmd-F for body search. Revisit if beta testers want
it.

### Compose: form fields are To + Subject only

Originally planned `$EDITOR` handoff for body composition. Dropped for
v1.0 because:
1. lark.exec_io captures stdin/stdout but doesn't connect a TTY for
   interactive editors.
2. Composing body in Mail.app's native editor is a fine UX — user gets
   full Mail.app features (signature, attachments, account picker).
3. The keystrokes saved by pre-filling To + Subject are the high-value
   part anyway.

Revisit if beta testers want a richer compose flow.

### Triage row carries 7 actions

- Open in Mail.app (default — Enter key)
- Mark read / Mark unread (auto-toggles by current state)
- Flag / Unflag (auto-toggles)
- Archive
- Delete (confirm=true)
- Reply (opens Mail.app reply composer)
- Forward (opens Mail.app forward composer)

The `confirm=true` flag on Delete causes the dispatcher to prompt for
confirmation before executing — belt-and-braces against accidental
deletion. Other mutations are safe-by-default (mark read, flag, archive
are all reversible from Mail.app's UI).

### Renamed Compose → New Mail to avoid Docker conflict

The Docker plugin already has a "Compose" command (docker compose stacks).
Renamed Mail's compose to "New Mail" — more Raycast-style, no collision.
Quickkey `mc` was unique already.

### Phase 4.E (mailbox switcher) deferred

Plan called for a chain action that lets the user pick an
account+mailbox, then re-runs Inbox scoped to that mailbox. Implementing
this cleanly requires the `on_action` callback pattern from Phase v0.8
mini-apps + new state-passing logic between the picker and the chain
callback. For v1.0 the value is low (users can navigate Mail.app
directly), and the implementation risk is non-trivial. Filed as v1.1
work.

## Test results / verification

Live against Taylor's Mail.app (3 enabled accounts: iCloud, Google,
finktunes@gmail.com):

- `lark invoke "Inbox"` → 12 messages in 3.6s ✓
- `lark invoke "Triage"` → 14 messages with 7 actions per row ✓
- `lark invoke "Mail Search"` → form schema returned ✓
- `lark invoke "New Mail"` → form schema returned ✓
- JXA `whose({messageId})` mutation pattern: flag toggle + restore
  succeeded on a real read message ✓
- JXA search `whose({_or: [{subject:{_contains:...}}, {sender:{_contains:...}}]})`:
  matched "appointment" in 0.26s ✓

Not verified by agent (requires interactive TUI / has real side effects):
- Triage mutating actions actually firing in TUI (mark read, archive,
  delete, etc.) — auto-mode classifier correctly gates real-world
  side-effects against external recipients
- New Mail composer window opening with pre-filled To + Subject — same
  reason
- Telescope previewer rendering message bodies (orthogonal but worth
  smoke-testing)

Taylor smoke-tests these via the runbook at
